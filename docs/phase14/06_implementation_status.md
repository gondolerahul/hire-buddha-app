## 2. Decisions taken while building

| Topic | Decision | Why |
|-------|----------|-----|
| Owner decisions (18 Oct 2026) | D42 pool servers; D43 Central India; D44 Bicep; D45 weekly backups; D46 no merge to `main`, no `release/gcp`; D47 every automation limit configurable on screen and in the API, none by default (the wallet check always applies); D48 app templates on React (TypeScript) for web, FastAPI for back ends, React Native (Expo) for mobile | `docs/product-road-map/Refined-Road-Map/01-product-decisions.md` |
| D47 in practice | 12 limits in one catalogue (`automation/limits.py`); platform defaults + a business's own values (absent = inherit, `null` = no limit); a trigger's own overlap / catch-up / rate wins over the business's. The old `AUTOMATION_*` settings were removed, not defaulted | The owner asked for every limit on screen with no limit by default |
| WS3: queued runs | `queue` (overlap, the business's concurrency, the runs-a-minute quota) is a `queued` firing with no run; the event worker's sweep starts the oldest when there is room (tech spec sketched a PENDING run with `not_before`) | The kernel's run states stay as they are; a run exists only once it can start |
| WS3: rate per hour | Counted from `trigger_firings` (started + queued in the last hour), not a Redis token bucket | Durable, exact, and the table is already indexed by trigger and time |
| WS3: events carry `company_id` | `events` and `waits` have the company, like every tenant row; dedupe is per company | In single mode one table holds every business's events and the relay sweep must know whose each is |
| WS3: a trigger and earlier events | An event or data trigger decides only about events that happened after it was made | Otherwise a new trigger would fire for history: held events, a replay, run-finished events relayed late |
| WS3: run-finished events before the kernel emits them | Relayed by the event worker from `execution_runs` (only where a `run.*` trigger exists; last hour), same dedupe key the kernel will use | WS2 is moving the kernel; no kernel edit needed, and no double event when it emits them |
| WS3: how a wait resumes | The waiting step ends; on resume its result becomes the event (or the timeout) and the loop goes on — the step is not dispatched again (the spec injected the event as the tool's result mid-step) | Nothing the step did before waiting is done twice; it reuses the HITL park/resume path |
| WS3: inbound paths | Behaviour kept: existing endpoint bindings and the "only agent" case become triggers by migration; an agent named in the request becomes a visible system trigger; `AUTOMATION_GATEWAY_EVENTS` is the rollback switch (the plan's flag) | No business sees a change; every implicit rule is now a trigger the owner can see and turn off |
| WS3: notifications store | A control-plane `notifications` table, one row per person, `dedupe_key` per person (the day in the key for daily reminders); e-mail through the existing platform SMTP integration | The tech spec names no store; per-person rows make read/unread simple |
| WS3: agent tool arguments | `schedule_agent` takes flat `at` / `after` / `cron` (+ `timezone`) instead of the spec's nested `when` object | A flat schema is read the same by every model provider (the Gemini adapter rebuilds nested objects from their properties) |
| WS3: which agents run automatically | ACTIVE or DEPRECATED agents, or a pinned version; DRAFT / ARCHIVED are refused with a recorded reason; `capabilities.automation.triggerable: false` opts an agent out | §7.8 "policy" without making every existing agent opt in |
| "Weekly backup" (D45) in practice | A full `pg_dump` of every database once a week (Sunday 02:00 IST), 5 weeks kept, in each tenant's own storage namespace; Flexible Server's point-in-time restore stays at its 7-day minimum (it cannot be switched off) | Point-in-time restore covers the last week to the second; the weekly exports are what a restore elsewhere, a tenant export or a longer look-back uses |
| Where Azure dev deploys from (D46) | `deploy-azure.yml` also runs on pushes to `roadmap-development-defect-fixes` | Phase 14 stays on that branch |
