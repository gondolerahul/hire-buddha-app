# 13 — Observability, Feature Flags, and Rollout (Cross-Cutting)

This document defines the **operational scaffolding** that every Track
plugs into: how telemetry events are emitted, how feature flags are
resolved, how new code paths are rolled out without blowing up.

If a Track adds a new flag or event, this document is the catalogue.

---

## 1. Principles

* **Every new code path is born behind a feature flag.** ON only when
  explicitly enabled in a tenant.
* **Every flag has a kill switch.** If the new path misbehaves, ops
  flips the flag OFF without a code change.
* **Every flag has a deletion date.** Listed in Track 9. Flags whose
  default has been ON for ≥30 days without negative signal are
  deleted.
* **Every event has a canonical envelope.** No more ad-hoc
  `logger.info(...)`.
* **Every new metric has a baseline measured before the flag flips ON**
  so we can detect regression.
* **Rollout is canary → 10% → 50% → 100%** with at least 24h between
  ramps unless a higher cadence is justified.

---

## 2. Telemetry event envelope

All events share one envelope.

```python
# core/telemetry.py  (NEW or extend existing)
@dataclass
class TelemetryEvent:
    event: str                       # "agent.loop.iteration_start"
    ts: datetime                     # UTC
    company_id: UUID | None
    user_id: UUID | None
    run_id: UUID | None
    entity_id: UUID | None
    iteration: int | None
    payload: dict                    # event-specific, JSON-serializable
    severity: Literal["debug","info","warn","error"] = "info"
```

Emitter:

```python
async def emit(event: str, **kwargs) -> None:
    """Emit a structured event to the local event bus.

    Backends:
      - Stdout JSON (always, for log aggregation pickup)
      - Optional Loki / OTel exporter if configured
      - Optional pubsub to Redis for SSE relay
    """
    ev = TelemetryEvent(event=event, ts=datetime.utcnow(),
                        company_id=kwargs.pop("company_id", None),
                        user_id=kwargs.pop("user_id", None),
                        run_id=kwargs.pop("run_id", None),
                        entity_id=kwargs.pop("entity_id", None),
                        iteration=kwargs.pop("iteration", None),
                        payload=kwargs)
    _LOCAL_BUS.publish(ev)
```

### 2.1 Naming convention

```
agent.<layer>.<verb>[_<qualifier>]
```

* `agent.loop.iteration_start` ✅
* `agent.critic.post_verdict` ✅
* `agent.tool.resilience.fallback_taken` ✅
* `agent_loop_iteration_start` ❌ (no dots)
* `AgentLoopIterationStart` ❌ (snake_case lowercase)

### 2.2 Cardinality discipline

* Per-run events: ≤30 per typical run.
* Per-iteration events: 5-10 per iteration.
* Per-step events: 3-5 per step.
* Per-tool-call events: 2 per tool call.

If a Track's events would exceed these, push aggregates into the
`StepHealthRecord` instead.

### 2.3 Master event catalogue

The Tracks each list their events. The complete catalogue lives in
the Grafana / Metabase dashboard config and the Phase 11
`docs/phase11/EVENTS.md` (generated by Track 9 from the Track docs).

## 3. Feature Flags service

### 3.1 Resolution order

```
1. entity.metadata_extensions.feature_flags[flag_key]
2. feature_flags row WHERE entity_id = e
3. feature_flags row WHERE company_id = c AND entity_id IS NULL
4. feature_flags row WHERE company_id IS NULL AND entity_id IS NULL
5. code default
```

First non-null wins.

### 3.2 API

```python
# core/feature_flags.py
class FeatureFlags:
    def __init__(self, db, redis):
        self.db = db
        self.redis = redis
        self._cache: dict[tuple, Any] = {}   # short-lived per instance

    async def is_on(self, flag_key: str, *,
                    company_id: UUID | None = None,
                    entity_id: UUID | None = None,
                    run_id: UUID | None = None,
                    default: bool = False) -> bool: ...

    async def get(self, flag_key: str, *,
                  company_id=None, entity_id=None, run_id=None,
                  default: Any = None) -> Any: ...

    async def set(self, flag_key: str, *,
                  enabled: bool | None = None, value_json: Any = None,
                  company_id=None, entity_id=None) -> None: ...
```

### 3.3 Caching

Process-level cache with 60-second TTL. The Redis pubsub channel
`feature_flag_invalidations` triggers immediate cache invalidation
when an admin flips a flag via the API.

## 4. Rollout discipline per Track

### 4.1 Standard rollout

```
Day 0     — Migration deployed; flag OFF in production.
Day 0+1h  — Flag ON for "dev" tenant only.
Day 1     — Flag ON for canary tenant (1 real customer); watch KPI dashboard.
Day 2     — Flag ON for 10% of tenants; watch for 24h.
Day 3-4   — Flag ON for 50%; watch for 24h.
Day 5     — Flag ON for 100%.
Day 35    — Flag deleted in Track 9.
```

If the KPI dashboard shows regression at any step:

1. Flip the flag back OFF.
2. Open an incident.
3. Patch.
4. Restart at canary.

### 4.2 Track-specific rollout notes

| Track | Rollout cadence | Notes |
|------:|-----------------|-------|
| 0 | Single PR, immediate | No flag — pure cleanup |
| 1 | Single PR | No flag — schema split keeps re-export shims |
| 2 | Canary → 10% → 50% → 100% over 7 days | Parity test gate |
| 3 | Canary → 25% → 100% over 4 days | Critic catch rate must rise; cost ≤ +15% |
| 4 | Canary → 10% → 50% → 100% over 5 days | Bandit needs ≥5 runs/arm before exploit |
| 5 | Canary on Meta-Agent runs only → 10% → 100% over 10 days | Risk amplified; longer canary |
| 6 | Canary → 10% → 50% → 100% over 5 days | Quality similarity ≥ 0.85 gate |
| 7 | Canary → 10% → 50% → 100% over 4 days | Cost per success must improve ≥10% |
| 8 | Canary → 10% → 50% → 100% over 4 days | Tool success rate watch |
| 9 | Deletes happen Day 30+ post each Track | Strict 30-day OFF window before deletion |

### 4.3 Canary tenant selection

A small list of internal-or-friendly tenants is maintained in
`backend/scripts/canary_tenants.json`:

```json
{
  "agent_loop.enabled": ["acme-corp-dev", "internal-test"],
  "critic_pipeline.v2_enabled": ["acme-corp-dev", "research-staging"],
  "meta_agent.board_routing": ["internal-meta-lab"]
}
```

CI rejects merges that change a flag's default ON without listing
canary tenants here.

| `kpi_daily_rollup.refresh_seconds` > 60 | > 60s | 9 |

### 5.3 Logging discipline

Severity guidelines:

* `debug` — per-iteration noise, only when debug log level on.
* `info` — successful state transitions (`iteration_start`, etc.).
* `warn` — recoverable issues (`agent.tool.resilience.fallback_taken`).
* `error` — unrecoverable in a single iteration (`agent.executor.failed`).

ERROR alerts page; WARN alerts in Slack channel.

## 6. Rollback playbook

### 6.1 Per-Track rollback

| Track | Rollback action | Time to restore |
|------:|-----------------|----------------:|
| 0 | Revert PR | minutes |
| 1 | Revert PR (schemas re-export shim makes this trivial) | minutes |
| 2 | Flip `agent_loop.enabled = false` everywhere | <1 min |
| 3 | Flip `critic_pipeline.v2_enabled = false` + `v1_compat = true` | <1 min |
| 4 | Flip `meta_review.v2_enabled = false`, `bandit.enabled = false` | <1 min |
| 5 | Flip `meta_agent.board_routing = false` | <1 min |
| 6 | Flip `memory.v2_canonical = false` (entity-level opt-out) | <1 min |
| 7 | Flip `planner.v2_enabled = false` | <1 min |
| 8 | Flip `tools.cost_resolver_v2_enabled = false`, `resilience_v2_enabled = false` | <1 min |
| 9 | Revert the deletion PR (no flag — code path is gone) | 15-30 min |

### 6.2 Database rollback

Every migration in [12](./12_data_model_and_migrations.md) has a
`downgrade()` method. Run via Alembic. Note:

* `p11t05_preserve_meta_cognition` downgrade is **destructive**
  (strips keys). Use only if rolling back the Track 5 code as well.
* `p11t08_usage_logs_attribution` downgrade drops the column —
  irreversible loss of attribution data. Prefer leaving the column
  in place even if Track 8 is rolled back.

### 6.3 Communication template

Every flag flip / rollback is announced in `#eng-agent-kernel` with
the template:

```
[T<NN>] <flag> → <ON|OFF> on <scope>
reason: <why>
expected impact: <metric and delta>
observer: <on-call name>
```

## 7. CI gates

Each Track's PR must pass:

1. `pytest` full suite green.
2. `mypy --strict` on the paths the Track touches.
3. `lint_ai_layout.py` green.
4. `lint_no_phase_narration.py` (Track 9) green (warning-only until
   Track 9, error after).
5. Migration dry-run on staging clone of prod data (CI step).
6. Canary tenant list updated (if default flag changes).
7. Telemetry events exist in `docs/phase11/EVENTS.md` index (auto-
   generated by a CI step).

## 8. Open questions

* Where does telemetry actually go? OTel + Loki? Honeycomb?
  Decision needed by Track 9. Until then, stdout-JSON + Redis pubsub
  for SSE is enough.
* Should flags evaluate **per-iteration** or **per-run**? Per-run for
  cost reasons. Track 2 evaluates flags inside
  `arq_jobs.run_execution_recursive` once.
* Should we expose flags in the **frontend** for admins? Yes — admin UI
  surfaces `feature_flags` rows + `set` endpoint. Out of scope for the
  agent kernel work, but the API endpoint exists from Track 2.
